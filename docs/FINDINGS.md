# TNT 弹道辅助 · 技术结论

这份文档只记录**被实验证实过的结论**，以及每条结论的证据等级。凡是没有写明
「真实对局」的，都是注入/离线验证，不要当成实测结果用。

术语：
- **真实对局**：两个账号在私服实际对打，数据来自对局过程中的实时采样。
- **注入/离线验证**：静态反汇编、内存镜像分析、或人为构造输入得到的结论。
- **sprite**：画面上的 QGraphicsItem 坐标（`BattleSpritePlayer` 的位置）。
- **role**：服务器同步点 `BattlePlayer+0x88`（角色对象坐标）。
- **距**：游戏内距离单位，1 距 = 82.5 屏幕 px（显示侧）。

## 一、弹道公式（子弹）

### 模型

离散帧积分，30 fps，屏幕 y 向下为正：

```
Q     = 1 - K
A(n)  = (1 - Q^n) / K
B(n)  = n - A(n)

x(n)  = x0 + vx0 * A(n) + w * B(n)
y(n)  = y0 + vy0 * A(n) + (G/K) * B(n)

vx0 = V0K * f * cos(θ)      f = 力度 / 100
vy0 = -V0K * f * sin(θ)
w   = WIND_MULT * wind_action       wind_action 正 = 顺射向
出膛点 = 角色位置 + MUZZLE * (cos θ, -sin θ)
```

### 常量

| 常量 | 值 | 含义 |
|---|---|---|
| K | 0.0186951412 | 每帧速度衰减系数 |
| G | 4.28938354 | 每帧² 重力加速度 (px) |
| V0K | 144.787175 | 满力初速 (px/帧) |
| WIND_MULT | 1.46643562 | 风力 → 加速度 |
| MUZZLE | 28.0 | 炮管长度 (px) |
| AIM_UP | 0.0 | 瞄准点 = 对手站立点（脚下） |
| TY_UP | 20.0 | 命中判定中心 = 脚底上 20 px（仅记录，不参与解算） |
| PX_PER_JU | 82.5 | 1 距 = 多少屏幕 px |
| SCREEN_SCALE | 1.98 | 屏幕 px / 世界单位（竞技模式实测） |
| CHARGE_K / CHARGE_B | 0.1990 / -0.0306 | 按住秒数 → 力度 |

### 拟合质量

用 3 条服务器权威弹道、39 个下发点重拟合：

| 模型 | rms |
|---|---|
| 出厂常量（6 参） | 6.446 px |
| 5 参重拟合（无角度偏置） | 4.722 px |
| **6 参 + 全局角度偏置（采用前）** | **2.071 px** |
| 7 参（过拟合风险） | 1.884 px |

单发残差：最好 1.009 px（max 1.635），最差 3.529 px。

> 最终采用的是**不含角度偏置的那组常量**（上表的 K/G/V0K/WIND_MULT/MUZZLE）。
> 原因：样本里的 `angle` 是「请求角」，真实发射角 = 请求角 + 地形角。
> 带偏置的拟合把地形角吸收进了物理常量里，运行时就重复补偿了。
> 运行时读的是 `actual`（= weapon + terrain），**不要再加偏置**。

### 力度充电公式

`force = CHARGE_K * 按住秒数 + CHARGE_B`，即 `0.1990 * t - 0.0306`。

用 4 个真实释放值标定（残差 ≤ 0.0037）：

| 按住 | 实测力度 | 公式 |
|---|---|---|
| 1.770 s | 0.3216 | 0.3216 |
| 2.004 s | 0.3678 | 0.3682 |
| 2.075 s | 0.3786 | 0.3823 |
| 2.781 s | 0.5228 | 0.5228 |

满力按住 5.18 s。旧公式（0.1940 / -0.0294）在 2.8 s 处低估 1.3 个力度点，
打远距离会系统性偏长。

**独立验证**：有一条轨迹只知道「按住 2.0 s」不知道力度，把它当自由参数反解
得到 36%，而充电公式预测 35.9% —— 这是独立于拟合的交叉验证。

### 验证等级

- ✅ **真实对局**：竞技模式 1078 px 实测命中（对手 1880 → 1477，−403）。
- ✅ 8 条真实弹道的残差 < 2 px。
- ⚠️ 剩余误差主要来自**按住充电的机械精度**（±0.3~0.5 力度点 ≈ ±6~10 px）
  和**每回合变化的风**，不是公式误差。

## 二、飞行（喷气背包）公式

### 与子弹公式完全不同

```
x(n) = x0 + vx * n
y(n) = y0 + vy * n + 0.5 * FLY_G * n²        n = 帧 @30fps
v    = FLY_V0K * force                        force ∈ 0..1
```

| 常数 | 子弹 | 飞行 | 比值 |
|---|---|---|---|
| V0K (px/帧/力度) | 144.787175 | **105.64** | 0.730 |
| G (px/帧²) | 4.28938354 | **2.28** | 0.532 |
| 空气阻力 K | 0.0186951412 | **0** | — |
| 风力耦合 | 有 | **无** | — |

四点差异：
1. **没有空气阻力** —— 飞行是纯抛物线（K = 0）；
2. **不受风力影响** —— 风 +1156 与 −1374 的样本残差相关系数 r = +0.22；
3. 初速更小（0.73 倍）；
4. 重力更小（0.532 倍）。

发射角就是表盘 `actual` 角，不需要额外补偿。

### 验证等级

- ✅ **真实对局**：8 条完整轨迹，速度方向吻合残差 0.0~1.0 px/帧，
  速度标定残差 rms 0.65 px/帧。

## 三、放大镜（体型变大）只改变受击体积

### 结论：力度公式不变

三条独立证据：

1. **变身是服务端通知驱动的**（注入/离线验证，符号链完整）：
   ```
   BattleNotify_Change_Item::kTitanFieldNumber
     → BattleChangeTitan::init / play
       → BattleRole::setTitan(bool)        (+0x4E 置位)
         → BattleRole::titanChanged()
           → BattleSpriteRole::setTitan(bool)
             → BattleSpritePlayer::onRoleTitanChanged()
   ```
   客户端开火路径完全不碰 titan 标志。

2. **客户端不参与弹道计算**（注入/离线验证）：
   `BattleConsole::onForceClicked @0x13583d4` 只把原始 `slider_fraction` 发给服务端；
   全库扫描 **0 个** float32 常量命中 G / V0K / K / FLY_G / FLY_V0K。
   客户端没有弹道积分器 ⇒ 服务端用同一套公式，放大镜不可能改变它。

3. **放大镜唯一改变的是渲染尺寸**：
   `BattleSpriteBomb::initPoint @0x1338580` 内含 `fmov d0, #2.00000000`
   ⇒ 精灵按 2× 绘制 ⇒ 受击包围盒线性 ×2、**面积 ×4**。

用户观感「密度变成原来的 2/3」= 命中容差变大后，原本差一点打不中的弹道开始命中。

### 验证等级

- ✅ **注入/离线验证**：上述三条证据充分。
- ⚠️ **真实对局验证缺失**：测试账号没有放大镜道具（背包、商城、道具池均未见），
  无法在真实对局中拿到变身状态做逐发测距。

## 四、隐身 + 飞行期间的位置：客户端拿不到

这是本项目最花时间的一个问题，结论是**数据边界问题，不是算法问题**。

### 结论

**隐身期间客户端根本没有对方的真实位置**——不是字段读错，是整个进程里没有这份数据。

### 证据 1：双端 12 Hz 同步采样，6 段真实隐身

真值 = 隐身方自己的 `self=`；误差 = 观察方客户端里该玩家的坐标与真值的距离。

| 段 | 观察方 → 目标 | 时长 | 目标实际移动 | sprite 误差（中位/最大） | role 误差（中位/最大） |
|---|---|---|---|---|---|
| 1 | 主机 → 客机 | 95.9 s | 683 px | **475 / 475 px** | 683 / 683 px |
| 2 | 主机 → 客机 | 78.4 s | 436 px | 418 / 418 px | 498 / 683 px |
| 3 | 主机 → 客机 | 99.6 s | 202 px | 363 / 363 px | 455 / 498 px |
| 4 | 客机 → 主机 | 98.9 s | 867 px | 507 / 507 px | 867 / 867 px |
| 5 | 客机 → 主机 | 70.7 s | 477 px | 290 / 290 px | 440 / 867 px |
| 6 | 客机 → 主机 | 78.2 s | 861 px | 313 / 384 px | 431 / 440 px |

**sprite 的中位数 == 最大值**意味着它在整个隐身期一帧都没动过，是彻底冻结，
不是"跟得不准"。role 冻结得更早（停在起飞点）。

### 证据 2：解除隐身的那一帧精确归位

```
t=4747.3  hide=1  sprite=2231,225   真值=2576,552   误差 475.3
t=4747.7  hide=0  sprite=2576,552   真值=2576,552   误差   0.0   ← 同一帧内
```

6 段全部如此（458/475/418/507/290/313 → 0.0）。⇒ 服务端在隐身期间不下发位置包。

### 证据 3：内存取证（真实对局 + 直接读进程内存）

用 `tnt_memeat findpair` 在观察方进程里全量搜索被隐身者的真实坐标
（int32 / float32 / float64 三种编码，671 MB 匿名内存、963 个区域、单次约 0.7 s）：

| 时刻 | 搜什么 | 命中 |
|---|---|---|
| 隐身 + 飞行中 | 真实坐标 | **0** |
| 同一次隐身 | 画面上的坐标（对照） | 1（sprite 的 QPointF）→ 证明扫描本身有效 |
| 隐身 + 飞行中 | 飞行**落点** | **0** |
| 隐身者**开炮那一瞬间** | 真实坐标 | **2~4 个**，误差 0 px |

排除取整误差：落点用 **±2.0 px 容差**再搜仍是 **0 命中**（695 MB / 976 区域）。

### 证据 4：行为学对照

- **可见飞行**：观察方画面一路跟到落点，全程 err = 0（同一套飞行机制）；
- **隐身飞行**：画面只播弧线前 ~0.7 s 就冻结，停在 63% 处。

同一个客户端，有数据就能播完，没数据才停在半路 —— 它手里确实没有落点。

### 外推也不行

6 段真实隐身里 `(落点x - 起点x) / (冻结x - 起点x)` =
2.52 / 1.92 / 1.00 / 2.19 / 1.42 / 1.59 —— 离散度极大，没有可用比例。

### 非内存通道也排除了（真实对局）

| 通道 | 结果 |
|---|---|
| 磁盘/回放 | 战场期间无任何战斗数据落盘，客户端不存回放 |
| 网络 | TLS 1.2 加密；5 s 窗口服务器→客户端仅 12 包 / 955 字节；明文搜索坐标 0 命中 |
| frida 解密 | 游戏只带 arm64 库，模拟器是 x86_64（arm64 靠转译），frida 无法 instrument |

服务端只发离散事件，不发逐帧位置。

### 「开炮瞬间真值出现」不是稳定通道

2/2 次复现，开炮瞬间会出现 2~4 个 int32 拷贝（活约 3 s，误差 0 px）。但是：
- 地址每次不同，落在战斗事件区，**没有稳定结构**；
- **画面精灵不一定跟着更新**（有一次 7 s 内都没动）；
- 而且**开炮会让隐身当场解除**（hide 1→0，1 秒内）——所以"能看到炮弹从哪飞出来"
  的真实原因是开炮解除了隐身，不是客户端另存了一份出膛点。

### 对实现的影响

`overlay/.../FrameBuilder.java` → `pickFreshPos()`：

- **删掉 role 兜底分支**（实测它永远比 sprite 差）；
- 永远输出 sprite，并上报 `pos_stale` / `stale_ms`，让界面区分"精确"和"过期"；
- hide = 0 时 sprite 精确（实测 0 px），hide = 1 时标记过期。

**可达到的精度分三段：**

| 阶段 | 精度 | 依据 |
|---|---|---|
| 可见 | **0 px** | 双端真实对局，hide=0 时 sprite 与真值逐次完全相等 |
| 隐身中 | 冻结（197~699 px） | 全堆 695 MB / 976 区搜真值 0 命中 |
| 开炮 / 解除隐身 | **0 px**（≤1 帧） | 服务端立刻下发真值 |

> 原始判据是「隐身+飞行全程 < 30 px」，该判据在客户端内存层面不可达。
> 这是数据可用性的边界，不是逆向没做够。

## 五、三处常量必须保持一致

```
core/aim_solver.py  ≡  private_server/ballistics.py  ≡  overlay/.../Solver.java
```

校验方式：

```bash
python private_server/ballistics.py     # 逐项断言 + 5×4×3 组 solve_target 对拍
```

`ballistics.py` 会 import `core.aim_solver` 并逐常量比对，同时用
5 角度 × 4 距离 × 3 高差共 60 组参数对拍 `solve_target`，误差 < 1e-9。

## 六、已知的坑

| 坑 | 说明 |
|---|---|
| `roles=` 字段错位 | 第 6 个字段是 `dead`，第 7 个才是 `hide`。读错会让整轮实验判成"隐身从未生效" |
| 风字段 `Config+0x470` | 已证伪：两场战斗全程恒为 69。风力走 `BattleWind` 的 MD5 哈希通道 |
| `/proc/PID/mem` | 会触发爱加密壳的反 dump，进程自杀。只能走 `process_vm_readv` |
| `state.facing` | 由 m11 符号推出，**不能可靠反映真实出膛方向**。实测有回合会朝反方向打 |
| 盘面角度 | 显示的是 `actual` = weapon + terrain，解算直接用它 |
| 反抛（>90°） | 盘面 117° 朝右 = 物理 63° 朝左，水平射向翻转 |
| 屏幕比例 | 竞技模式 1.98 屏幕px/世界px；旧值 0.648 偏小 3 倍 |
